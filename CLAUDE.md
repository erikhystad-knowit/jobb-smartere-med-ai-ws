# Wiki schema — Jobb smartere med AI

This repository is a **personal knowledge wiki** maintained almost entirely by you,
the LLM agent. The human owner is a participant in the Knowit Academy course
*"Jobb smartere med AI"*. The wiki accumulates what they learn — primarily from
**case work**: real or course-assigned work tasks where AI is applied, tried,
evaluated, and reflected on.

The pattern this implements is described in `llm-wiki.md`. Read that file if you
need the rationale; read *this* file for the conventions.

---

## 1. The layers

| Layer | Directory | Who owns it |
|---|---|---|
| **Raw sources** | `raw/` | The human. Immutable. |
| **The corpus** | `korpus/` | Generated by `scripts/korpus.py` from `raw/caser/<case>/`, plus your triage. See §5.8. |
| **The wiki** | `wiki/` | You. You create, update and cross-link every page. |
| **The schema** | `CLAUDE.md` (this file) | Both. Co-evolved as conventions prove themselves. |

Two kinds of case exist and they are handled differently:

- **Small case** — a note, a prompt log, a handful of files. One page in
  `wiki/caser/<slug>.md`, sources get `kilder/` pages as usual (§5.2–5.3).
- **Corpus case** — a large body of material (hundreds of e-mails, dozens of
  documents) where *getting an overview* is itself the task. The material is
  inventoried into `korpus/`, triaged in batches, and synthesised into a case
  folder `wiki/caser/<slug>/` (§5.8, §6.6). Individual e-mails and documents do
  **not** get `kilder/` pages.

A corpus case still produces **two kinds of knowledge**, and they must stay
separate: *what the material says* (the domain — people, topics, decisions,
timeline) and *what I learned about working with AI* by doing it (the case
page proper). The second is what feeds `teknikker/`, `verktoy/` and
`oversikt.md`.

## 2. Hard rules

1. **Never modify anything under `raw/`.** Not to fix typos, not to reformat, not
   to add frontmatter. It is the source of truth and must stay byte-identical to
   what was dropped in. Read-only, always.
2. **Every ingest updates `wiki/index.md` and appends to `wiki/log.md`.** No
   exceptions. A page that is not in the index is invisible to future sessions.
3. **Never silently drop a contradiction.** If a new source contradicts an
   existing claim, record both and flag it (see §6.4). Do not overwrite the old
   claim as if it were never made.
4. **Cite the source on every factual claim.** Link to the `wiki/kilder/` page,
   not to the raw file. In a corpus case, cite by corpus ID instead: `[EM-042]`
   for an e-mail, `[[caser/<slug>/dokumenter/fin-003-navn|FIN-003]]` for a
   document that has its own page, `[FIN-003]` for one that doesn't. Multiple:
   `[EM-042, EM-051]`. IDs resolve through `korpus/<slug>/manifest.csv`. If the
   material carries its own IDs in filenames (`EM-001_…`, `OPS-005_…`) those are
   used; otherwise the script assigns `E-001` / `D-001`. Bare IDs are what
   `korpus.py dekning` greps for — keep the exact `ABC-123` form.
5. **One concept, one page.** If you find yourself explaining the same technique
   on three pages, extract it into `wiki/teknikker/` and link to it.
6. **Ask before restructuring.** Creating pages and updating links is your job and
   needs no permission. Renaming directories, changing frontmatter schemas, or
   moving many pages at once is a schema change — propose it first.
7. **Corpus material is the owner's work data.** Don't paste e-mail bodies into
   wiki pages beyond short quotes that carry a point. Summarise, cite the ID.
   Never send corpus content to any external service other than the model
   you're running on.

## 3. Language

- **Wiki pages (`wiki/**`) are written in Norwegian (bokmål).** That includes
  headings, body text, index entries and log entries. These are notes the owner
  reads and reuses at work.
- **This schema file is in English.** So is any commentary you write *to* the
  owner in chat about process.
- **File and directory names are ASCII-safe**: lowercase, hyphenated, no `æ ø å`.
  Transliterate: `æ`→`ae`, `ø`→`oe`/`o`, `å`→`aa`/`a`. Prefer the shorter form
  when unambiguous (`verktoy`, `loesning` → `losning`). Keep the Norwegian title
  intact inside the page's frontmatter `title:` field.
- Keep technical terms in whatever form the owner actually uses — *prompt*,
  *context window*, *agent* do not need forced translations.

## 4. Directory layout

```
raw/                  Immutable sources, exactly as received
  assets/             Images and attachments referenced by sources
  caser/<slug>/       Bulk material for a corpus case, in whatever folder layout it came in.
                      E-mail: .eml / .msg / .mbox, or .md with `**Fra:**` header lines.
                      Thread folders named TH-NNN are used as threads.
                      Documents: .pdf / .docx / .pptx / .xlsx / .csv / .txt / .md / .html;
                      the same ID in several formats is one item.
korpus/<slug>/        Derived from raw/caser/<slug>/ — see §5.8
  manifest.csv        One row per item: ID, date, sender, subject, thread, … (generated)
  tekst/E-001.md      Extracted plain text per item, attachments inlined (generated)
  triage.csv          Your per-item classification (hand-maintained, NOT regenerable)
scripts/korpus.py     Inventory + coverage check. `uv run scripts/korpus.py --help`
wiki/
  index.md            Catalog of every page. Content-oriented. Read this first.
  log.md              Append-only chronological record. Newest entry at the bottom.
  oversikt.md         The evolving synthesis — the "what do I actually believe now" page
  kilder/             One page per ingested source: summary + takeaways
  caser/              One page per small case; one folder per corpus case:
    <slug>.md           small case
    <slug>/             corpus case — see §5.8
  teknikker/          Reusable methods — prompting patterns, workflows, ways of working
  verktoy/            Tools — Claude, Copilot, NotebookLM, whatever gets used
  innsikter/          Filed-back answers: comparisons, analyses, conclusions from queries
  maler/              Page templates. Copy these when creating a new page.
    korpus/           Templates for the pages inside a corpus case folder
```

## 5. Page types

Every page starts with YAML frontmatter. The fields below are the contract —
keep them consistent so the index stays generatable and Dataview-style queries
remain possible later.

### 5.1 Common frontmatter

```yaml
---
title: Norwegian page title
type: kilde | case | teknikk | verktoy | innsikt | oversikt | korpus | tema | person | dokument
opprettet: YYYY-MM-DD
oppdatert: YYYY-MM-DD
tags: [kebab-case, norwegian]
---
```

### 5.2 `kilder/` — source pages

One page per item in `raw/`. The bridge between a raw file and the wiki.
Extra frontmatter: `kilde:` (relative path into `raw/`), `kildetype:`
(notat | artikkel | slides | transkripsjon | samtale | annet), `dato:` (the
source's own date, if it has one).

Sections: **Sammendrag** (3–6 sentences) · **Hovedpoenger** (bulleted, each one
linkable) · **Relevans for eget arbeid** · **Koblinger** (wikilinks out).

### 5.3 `caser/` — case pages (the centre of gravity)

This is the primary source type for this wiki. A case page is a record of
applying AI to a real task. Extra frontmatter: `status:` (paagaaende | ferdig |
henlagt), `verktoy:` (list of tool page names), `teknikker:` (list of technique
page names).

Sections, in order:

1. **Kontekst** — what the task was, what the constraints were, what "done"
   looked like.
2. **Hva jeg prøvde** — the actual approach. Include real prompts verbatim in
   fenced blocks; a paraphrased prompt is nearly worthless later.
3. **Hva som skjedde** — the outcome, honestly. Including the parts that failed.
4. **Vurdering** — did this beat doing it by hand? Where did it save time, where
   did it cost time, what did it get wrong.
5. **Overførbart** — the generalisable lesson. **This is the section that matters
   most.** If a lesson here is reusable, it should become or update a page in
   `teknikker/`.
6. **Koblinger**

For a corpus case this page lives at `wiki/caser/<slug>/case.md` and is about
the *method*: how the overview was built, which prompts were used for triage
and synthesis, how long each phase took, what the AI misclassified, what the
owner had to correct. The domain content lives in the sibling pages (§5.8).

### 5.4 `teknikker/` — technique pages

A reusable way of working. Sections: **Hva det er** · **Når det virker** ·
**Når det ikke virker** · **Eksempel** (concrete, from a real case) ·
**Erfaringsgrunnlag** (links to the cases this is drawn from — a technique
backed by three cases is stronger than one backed by zero).

### 5.5 `verktoy/` — tool pages

Sections: **Hva det er** · **Hva jeg bruker det til** · **Styrker** ·
**Svakheter / friksjon** · **Brukt i** (case links).

### 5.6 `innsikter/` — filed-back answers

When a query produces something worth keeping — a comparison, an analysis, a
conclusion — file it here rather than letting it die in chat. Extra frontmatter:
`spoersmaal:` (the original question). Sections: **Spørsmål** · **Svar** ·
**Grunnlag** (which pages this was synthesised from) · **Usikkerhet**.

### 5.7 `oversikt.md` — the synthesis

A single page answering "what do I currently believe about working smarter with
AI?" Revised, not appended to. It should read as a coherent position, with the
strongest claims first and open questions at the bottom. Update it when a case
or source meaningfully shifts the picture — not on every ingest.

### 5.8 Corpus cases — `korpus/<slug>/` and `wiki/caser/<slug>/`

**`korpus/<slug>/`** is the working layer between raw files and wiki pages.

- `manifest.csv` and `tekst/` are generated by `uv run scripts/korpus.py
  inventar <slug>`. Re-run it whenever files are added; IDs and thread IDs are
  stable across runs (native IDs from filenames and `TH-` folders when present,
  else generated `E-001` / `D-001` / `T-001`). Never hand-edit these. Read
  `tekst/<ID>.md` instead of raw files — attachments are already inlined, and
  `duplikat_av` tells you when a document is also an e-mail attachment.
- `triage.csv` is yours and is **not** regenerable — treat it like wiki content.
  One row per ID:

  | Column | Content |
  |---|---|
  | `id` | `E-001` / `D-001` |
  | `relevans` | `hoy` · `middels` · `lav` · `stoy` (definitions below) |
  | `tema` | tema slugs, `;`-separated |
  | `personer` | person slugs, `;`-separated — only people who *act* in it |
  | `oppsummering` | one line, Norwegian, what this item *adds* |
  | `status` | `triagert` · `syntetisert` |

  Relevance: **hoy** — carries a decision, commitment, figure, deadline,
  disagreement, or is the authoritative version of something. **middels** —
  discussion or context that shapes a topic. **lav** — logistics, scheduling,
  "ok, takk". **stoy** — newsletters, auto-replies, exact duplicates.

**`wiki/caser/<slug>/`** holds the pages. Templates in `wiki/maler/korpus/`.

| Page | `type` | What it is |
|---|---|---|
| `oversikt.md` | korpus | **Read first.** One-screen answer to "what is this material about and where does it stand", then links to every page in the folder. Acts as the case's own index — global `index.md` links here, not to every tema/person. |
| `case.md` | case | The AI-method record (§5.3). Feeds `teknikker/` and `verktoy/`. |
| `sporsmal.md` | korpus | The owner's guiding questions and current answers; plus unresolved items, gaps and contradictions (§6.4). |
| `tidslinje.md` | korpus | Dated events, one line each, cited. |
| `beslutninger.md` | korpus | Decision log: date · decision · who · basis (IDs) · status (gjeldende / endret / omgjort). |
| `katalog.md` | korpus | Generated table of every item grouped by tema and thread — `korpus.py katalog <slug>`. Never hand-edit. |
| `tema/<tema>.md` | tema | One per topic. **The main synthesis unit.** 6–15 per case is the healthy range. |
| `personer/<navn>.md` | person | One per person who matters: role, what they want, what they decided/committed to. |
| `dokumenter/d-007-<navn>.md` | dokument | Only for `hoy` documents and `middels` ones substantial enough to need a summary. Others live in the catalog. |

All pages in the folder carry extra frontmatter `case: <slug>`. Tema, person
and dokument pages also carry `kilder: [E-012, D-003, …]` — the IDs they are
built from, so coverage can be checked and the page rebuilt later.

Threads (`TH-001` / `T-001`) are a reading unit, not a page type: triage and synthesis
read a whole thread at once, but its content lands on tema pages.

## 6. Workflows

### 6.1 Ingest

Triggered by: *"les inn X"*, *"her er et nytt case"*, a new file appearing in `raw/`.

If the new material is a folder under `raw/caser/`, or more than ~20 files at
once, use §6.6 instead.

1. **Read the source completely.** If it references images in `raw/assets/`, view
   them separately — you cannot read inline images in the same pass as the text.
2. **Discuss before writing.** Tell the owner the key takeaways as you see them
   and what you intend to update. For case work especially, ask what they want
   emphasised — they were there, you weren't. Keep this short.
3. **Write the source page** in `wiki/kilder/` (or the case page in `wiki/caser/`
   if the source *is* a case).
4. **Propagate.** Walk the wiki and update everything the new material touches:
   technique pages gain evidence, tool pages gain experience, contradicted claims
   get flagged, `oversikt.md` gets revised if the picture actually moved. A single
   source legitimately touches 5–15 pages. Touching one page is usually a sign you
   did not propagate.
5. **Create missing pages.** If the source leans on a concept with no page, make one.
6. **Update `wiki/index.md`.**
7. **Append to `wiki/log.md`.**
8. **Report** what you touched, grouped by page type.

### 6.2 Query

Triggered by a question about the accumulated material.

1. Read `wiki/index.md` first to locate relevant pages. Drill into those pages;
   do not grep the whole wiki blindly, and do not re-read `raw/` unless the wiki
   pages are genuinely insufficient.
   For a corpus case the path is: `caser/<slug>/oversikt.md` → the relevant
   `tema/` pages → `katalog.md` / `triage.csv` to find specific IDs →
   `korpus/<slug>/tekst/<ID>.md` only to verify or quote.
2. Answer with citations as wikilinks to the pages used.
3. **Offer to file the answer back** into `innsikter/` when it has lasting value.
   A good comparison or conclusion is as valuable as an ingested source.
4. Log substantive queries (§6.5). Skip logging trivial lookups.

### 6.3 Lint

Triggered by: *"lint"*, *"helsesjekk"*. Produce a report; do not fix silently.
Check for:

- Contradictions between pages.
- Stale claims a newer source has superseded.
- Orphan pages — nothing links in.
- Concepts mentioned repeatedly with no page of their own.
- Technique pages with a thin `Erfaringsgrunnlag` (claims unsupported by cases).
- Index entries pointing at pages that no longer exist, and pages missing from
  the index.
- Gaps worth filling — good next questions, sources worth hunting down.
- For each corpus case: run `uv run scripts/korpus.py dekning <slug>` and
  report untriaged items and `hoy` items no page cites. Also tema pages whose
  `kilder:` frontmatter cites IDs that no longer exist.

Present findings grouped by severity, then ask what to fix.

### 6.4 Flagging contradictions

Inline, at the point of the claim:

```markdown
> [!konflikt] Motstrid
> [[kilder/kilde-a]] hevder X, mens [[kilder/kilde-b]] (nyere) hevder Y.
> Uavklart per 2026-10-22.
```

Keep both claims visible. Resolve only when evidence actually settles it, and say
what settled it.

### 6.5 `log.md` entries

Append-only, newest at the bottom. The `## [` prefix is load-bearing — it makes
the log greppable (`grep "^## \[" wiki/log.md | tail -5`).

```markdown
## [YYYY-MM-DD] ingest | Tittel på kilden
Kort beskrivelse. Sider berørt: [[a]], [[b]], [[c]].
```

Types: `ingest` · `case` · `korpus` · `query` · `innsikt` · `lint` · `skjema` (schema change).

A corpus case logs **one entry per phase** (§6.6), not per item:
`## [2026-10-23] korpus | <slug> — triage 3/10 (E-061–E-090)`. Include counts
and what changed; don't list every page touched if it's more than ~15 — name
the folders instead.

### 6.6 Corpus ingest

Triggered by: a folder appearing under `raw/caser/<slug>/`, or *"les inn
caset"* when the material is large. Phases are separate turns — stop and
report between them. Each phase gets its own log entry.

**Phase 0 — Inventory.** `uv run scripts/korpus.py inventar <slug>`. Report to
the owner: counts, threads, date span, word total, extraction failures (scanned
PDFs need OCR — say which), documents that are also attachments. Create
`wiki/caser/<slug>/` from `wiki/maler/korpus/` with `case.md` and a skeleton
`oversikt.md`, and add the case to `wiki/index.md` now, so it is never an orphan.

**Phase 1 — Purpose.** Before reading anything in depth, ask the owner, briefly:
- What is the overview *for*? (a decision, a handover, a status report, finding
  a specific thing?)
- Which 3–7 questions must it answer? → `sporsmal.md`, "Styrende spørsmål".
- Who are the key people, and who is the owner in this material?
- What do they already know, so we don't spend effort re-deriving it?
Record the answers in `case.md` → Kontekst. The guiding questions decide what
`hoy` means for this case.

**Phase 2 — Triage.** Every item gets a `triage.csv` row.
- Batch by **thread**, not by ID order: a batch is a set of whole threads
  (plus standalone documents), ~15–20k words (`ord` column). For 240 e-mails +
  40 documents expect roughly 8–15 batches.
- Run batches as parallel subagents. Each gets: the guiding questions, the
  relevance definitions (§5.8), the current tema list (or "propose tema freely"
  on the first round), the list of `tekst/` files to read, and the exact CSV
  columns to return. Subagents return rows; **you** merge them into
  `triage.csv` — subagents never write files.
- After the first round, consolidate the free-form tema suggestions into 6–15
  tema. Show the list to the owner before fixing it. Then remap the `tema`
  column; re-read only the items where the mapping is ambiguous.
- Spot-check: read ~10 items yourself across relevance levels and compare.
  Record the disagreement rate in `case.md` — it is the honest measure of how
  far the triage can be trusted.

**Phase 3 — Synthesis.** One tema at a time (parallelisable):
read every `hoy` and `middels` item tagged with the tema, in date order, and
write `tema/<tema>.md`. Then `dokumenter/` pages for `hoy` documents, then
`personer/`. Set `status: syntetisert` in `triage.csv` for what you covered.

**Phase 4 — Cross-cutting.** Build `tidslinje.md` and `beslutninger.md` from
the tema pages (go back to the text only to verify). Collect contradictions,
gaps and unanswered guiding questions in `sporsmal.md`. Write `oversikt.md`
last — it summarises the tema pages, not the raw material.
Run `korpus.py katalog <slug>` to regenerate `katalog.md`.

**Phase 5 — Coverage.** `uv run scripts/korpus.py dekning <slug>` must show 0
untriaged and 0 uncited `hoy`. Explain any exceptions.

**Phase 6 — Reflection.** Fill in `case.md` (prompts verbatim, time spent per
phase, what the AI got wrong, what the owner corrected). Propagate as in §6.1:
`teknikker/`, `verktoy/`, global `oversikt.md`, `index.md`, `log.md`.

**Adding material later:** re-run inventory (existing IDs keep their numbers),
triage only the new IDs ("nye siden forrige kjøring"), update affected tema
pages, flag anything that contradicts earlier conclusions (§6.4).

## 7. Linking

- Obsidian-style wikilinks: `[[caser/mitt-case]]`, or `[[caser/mitt-case|lesbar tekst]]`.
- Link paths are relative to `wiki/`.
- **Link generously.** The value of this wiki is in the connections, not the pages.
  A case with no outbound links is a dead end.
- Every new page needs at least one inbound link from an existing page, plus its
  index entry. Create the inbound link in the same pass — otherwise you have made
  an orphan.

## 8. Evolving this schema

These conventions are provisional. When a convention repeatedly gets in the way,
say so and propose a change rather than quietly working around it. Log accepted
schema changes with the `skjema` type so the reasoning survives.
